# v3.7.1 배포 및 성능·설치 비용 검증 결과

2026-11-04 UTC. 실제 배포 커밋은 `d00b4882c55704e5d83899ffd3820946aa9c15fa`다.
[PR #398](https://github.com/JeongJaeSoon/agent-guard/pull/398)을 병합하고
[v3.7.1](https://github.com/JeongJaeSoon/agent-guard/releases/tag/v3.7.1)과
[Homebrew #25](https://github.com/JeongJaeSoon/homebrew-tap/pull/25)를 배포했다.
이번 버전은 JSON 복구 수정과 진단 보강이다. 아래의 큰 성능 개선을 낸 실험용 scanner는 배포하지 않았다.

## 해결한 문제와 남은 문제

- **수정:** jq 1.8.1이 깊은 JSON을 `<skipped: too deep>`로 잘라 출력하면서 성공 종료하는 문제를 실제 재현했다. 중간 JSON 복구 실패 시 보존한 원본 envelope로 기존 독립 복구 경로를 실행하도록 최소 수정했다. 깊이 2000의 배열 구조를 보존하고, 두 호스트의 독립 기대 출력·정상 marker 문자열도 검사했다. 공개 v3.7.1을 실제 jq 1.8.1로 실행한 회귀 검사도 4/4 성공했다.
- **진단 보강:** scanner readiness 실패 이유를 고정된 비민감 코드로 표시한다. timeout, fail-open/closed 정책과 경고 빈도는 유지했다. Intel CI는 differential·호스트 반복·audit 단계를 나누고 진행 로그와 checkpoint를 보존한다.
- **미해결:** 최초 Intel 호스트 불일치는 fixture/stdout/stderr가 없어 원인 미확정이다. 후속 성공은 원인 해결의 증거가 아니다. 별도의 `1bbd6cf` Intel job도 제한 시간에 도달했으나 로그가 404이고 artifact가 없어 느려진 정확한 단계·인프라 원인을 특정하지 못했다. 누적 실행 지연, scanner 준비 지연, runner 문제는 가설로 남는다. 제한 시간을 늘리거나 기대값을 완화하지 않았다.

## 설치 시: 실제 공개 배포본 비교

Linux x64, 외부 cgroup 4CPU/16GiB, 동일 컨테이너 이미지에서 v3.7.0/v3.7.1 순서를 교대한 **3쌍의 새 설치** 중앙값이다. Rust·Go·C 컴파일러는 없고 jq/git/공식 gitleaks는 미리 설치했다. 실제 네트워크 다운로드, 검증, 압축 해제, 기본 shell 설정을 포함한다. 의존성 설치·이미지 빌드·Claude/Codex 앱 등록 시간은 포함하지 않는다. Docker 자체의 별도 자원 제한이 적용됐다고 주장하지 않는다.

| 지표 | 공개 v3.7.0 | 공개 v3.7.1 |
|---|---:|---:|
| 설치 완료 시간 | 1.70초 | 1.68초 |
| CPU 시간 합 | 0.84초 | 0.83초 |
| 최대 자식 RSS | 44.7MiB | 44.5MiB |

표본 수와 네트워크 변동을 고려하면 **설치 비용이 비슷하다**는 관측이다. 작은 차이를 성능 개선으로 주장하지 않는다. 설치의 표본 RSS 합은 측정하지 않았다. 별도의 실제 v3.7.0→v3.7.1 업데이트 3회는 중앙값 2.02초 / CPU 0.92초 / 최대 자식 RSS 44.9MiB였다. 기존 local note 보존과 smoke 검사 모두 통과했다. 버전을 지정하지 않는 `latest` 설치도 실제 v3.7.1을 설치했다.

## 사용 시: 구현한 후보와 채택 판단

| 후보 | 실제 결과 | 판단 |
|---|---|---|
| Rust `prepare-v1` 출력 준비 통합 | 준비 단계 자체는 크게 단축됐지만, v3.7.0 대비 전체 CLI 지연 약 3%, CPU 약 2.5~2.9% 개선 | 10% 채택 기준 미달로 기각 |
| gitleaks regex backend 변경 | 공식 배포 scanner 대비 목표 경로 지연 48.2~66.8%, CPU 47.9~66.5% 감소 | Homebrew scanner 대비 지연 14~37% 회귀로 일괄 교체 기각 |
| JSON 복구 및 readiness 진단 | 정확성 결함 수정과 원인 관측 개선 | v3.7.1 채택. 속도 개선으로 계상하지 않음 |

가장 큰 관측 병목은 전체 셸 재작성 필요성이 아니라 **외부 scanner의 반복 초기화**였다. 공식 gitleaks 8.30.1의 Wazero JIT 초기화는 `version`에도 약 317ms가 들었다. 같은 scanner 소스와 Go 1.26.0으로 regex backend만 바꾼 대조 빌드·후보를 만들어 검사했다. 후보는 공식 gitleaks 릴리스가 아니며 같은 버전 문자열 대신 파일 해시·모듈 그래프로 구분한다.

최종 scanner 비교는 실제 공개 v3.7.0 CLI/core를 양쪽에 그대로 사용하고 scanner만 바꿨다. **실제 적용된 2CPU/1GiB/swap0** 아래, 동일 입력·정책·설정으로 두 호스트, audit off/cold/warm, 21입력, 9쌍을 비교했다. 상태별 runner는 달라 각 실행 내부의 교대 비교만 해석한다. 전체 126개 비교에서 독립 기대 출력 검증을 통과했고 일반 경로의 지연·CPU 5% 초과 회귀는 없었다.

| 목표 경로 | 공개 scanner → 실험 scanner 지연 | 지연 감소 | CPU 감소 |
|---|---:|---:|---:|
| Claude, cold | 972.7 → 361.5ms | 62.8% | 62.6% |
| Codex, cold | 967.1 → 368.9ms | 61.9% | 61.7% |
| Claude, off | 921.8 → 306.4ms | 66.8% | 66.5% |
| Codex, off | 917.4 → 311.7ms | 66.0% | 66.0% |
| Claude, warm | 669.8 → 347.0ms | 48.2% | 47.9% |
| Codex, warm | 674.6 → 348.1ms | 48.4% | 48.2% |

같은 최종 실행의 동시 요청 4개 부하에서는 처리량 **1.24→3.72건/초**, 최대 자식 RSS **64.4→36.5MiB**, 표본 RSS 합 **301.0→194.4MiB**였다. 순차 부하는 1.09→3.19건/초였다. RSS 합은 10ms 표본으로 공유 페이지가 중복되고 짧은 피크를 놓칠 수 있으며, 최대 자식 RSS와 전체 동시 메모리는 다르다. 다른 실행의 절대 시간을 이 표와 섞지 않는다.

이 수치는 **미채택 실험 결과**다. 실제 Homebrew 8.30.1은 이미 빠른 stdlib regexp 구현이라 동일 교체가 회귀했다. 따라서 모든 사용자에게 해당 개선이 제공됐다고 말할 수 없다. 신규 scanner의 공식 공급·유지보수·업데이트·복구 경로도 남은 채택 조건이다.

소스/Git marketplace 경로도 실제 v3.7.0 소스, helper 부재 조건에서 별도 측정했다. 두 호스트 목표 지연 약 45~47% 감소를 관측했지만, 이는 4CPU/16GiB 로컬 단일 목표 fixture 9쌍이다. 별도 기본 경로 trace에서 native 실행 0을 확인했다. 실제 Claude/Codex 앱의 marketplace 등록·이벤트 전달 시험으로 확대 해석하지 않는다.

## 설치 비용을 더 지불하는 선택의 손익

동일 compiler·플래그, 미리 받은 모듈과 빈 빌드 캐시로 소스 빌드를 3쌍 교대했다. 로컬 4CPU/16GiB 조건이며 위 CI 측정과 다르다.

| 지표 | 대조 scanner 빌드 | 실험 scanner 빌드 |
|---|---:|---:|
| 빌드 시간 | 27.90초 | 30.89초 |
| CPU 시간 | 92.08초 | 100.70초 |
| 최대 자식 RSS | 286.7MiB | 809.5MiB |
| 표본 RSS 합 | 563.1MiB | 845.9MiB |

추가 빌드 비용은 약 3초·CPU 8.6초다. 같은 로컬 조건에서 다시 빌드한 대조/후보로 측정한 목표 fixture에서는 지연 절감은 약 **5회**, CPU 절감은 약 **12회**의 호출로 이 추가 비용을 상쇄했다. 이는 해당 작업의 예시이며 일반 호출·사용자 설치의 보편적 손익분기점이 아니다. **메모리 피크는 반복 사용으로 상쇄되지 않는다.** 낮은 메모리 장치에는 중요한 제약이다.

사전 빌드 바이너리를 제공하면 사용자가 이 컴파일 비용을 지불하지 않는다. 동일 gzip 설정의 scanner 단일 파일 압축 크기는 8.104→8.065MB였고, checksum+tar 해제 7쌍 중앙값은 252.5→239.6ms였다. 전체 공식 배포 archive나 네트워크 설치 시간을 비교한 결과는 아니다. 큰 실행 이득을 위해 반드시 더 비싼 사용자 설치가 필요한 것은 아니라는 관측이다.

## 정확도·배포·호환성

- Scanner 후보는 네 플랫폼 각각 corpus 230입력 × 3구현 불일치 0, 호스트 계약 90건 실패 0이며 upstream/race 검사도 통과했다. 독립 기대값, Unicode/비정상 UTF-8/NUL/metadata/placeholder/제한 경계를 포함했다. 과도 마스킹이나 보안 정책 완화를 성능으로 인정하지 않았다. 모든 regex 의미를 증명한 것은 아니다.
- 제품 최종 head `3099293`와 release merge `d00b488`의 필수 CI 각 8개가 성공한 뒤 배포했다. head 검사 39개는 38성공+CodeRabbit 1skip, merge Actions 30개는 모두 성공이다.
- 네 플랫폼 실제 native differential 각 1024건, 호스트 90건, Intel은 같은 90건 3회, audit 검증을 통과했다. 최종 커밋 packaged 성능 gate도 통과했으나 기준은 pre-Rust `9a0ee`이므로 v3.7.0 대비 새 개선이라고 하지 않는다.
- [공개 검증 run 41911796757](https://github.com/JeongJaeSoon/agent-guard/actions/runs/41911796757)은 7/7 성공이다. 네 플랫폼 공개 설치·3.7.0에서의 업데이트·실패 복귀 44건씩, Homebrew 세 플랫폼 구버전 업그레이드·canonical tap 새 설치를 확인했다. 검증기는 증거 브랜치 `5aaf064`이며 실제 공개 CLI/core·태그·해시를 검사한다.
- 공개 자산 15개 SHA-256과 sidecar, 공개 archive/개별 native/정확한 release CI artifact의 바이트 일치를 확인했다. Homebrew main formula도 공개 자산과 동일하다. v3와 v3.7.1은 release commit, v3.7.0과 legacy v1은 기존 commit을 유지한다.
- 사용자 문서 EN/KO/JA를 함께 갱신했다. 설치·업데이트 명령, 호스트 계약에 의도적 호환성 변경은 없으며 **v4 필요성은 입증되지 않았다.** 기존 `AGENT_GUARD_EXPERIMENTAL_REDACTOR=shell` 복구 선택을 유지한다. Git marketplace/source-only 설치는 helper 없이 기존 셸 경로로 실행한다. 실제 호스트 앱 내 모든 설치 조합의 무결함을 보증하는 시험은 아니다.
