# 설치와 반복 사용 비용의 교대 비교 — 2026-11-04

이 기록은 채택 전 scanner 후보의 추가 실험이다. v3.7.1에 이 성능 후보를
포함하거나 사용자 scanner를 교체하지 않는다. 실제 기본 설치의 전체 소요
시간을 측정한 자료도 아니다. 네트워크·패키지 관리자·호스트 등록 비용은 제외한다.

## 조건과 원시 자료

- Linux x64, 실제 외부 cgroup 4 CPU / 16 GiB. 2 CPU / 1 GiB CI와 구분한다.
- 공개 Agent Guard v3.7.0 CLI·core를 양쪽에서 그대로 실행한다.
- 공식 gitleaks 8.30.1, 같은 소스·Go 1.26.0의 원래 의존성 대조군, go-re2
  1.13.0 후보를 구분한다. binary hash와 archive hash는 `packages.json`.
- cold build는 각 실행마다 빈 GOCACHE를 쓰고 의존성 module cache는 이미
  준비했다. 인터넷을 사용하지 않는다. filesystem cache를 비우지는 않았다.
- 빌드 3쌍, 사전 빌드 압축 해제 7쌍, 두 호스트의 다중 문자열 출력 각 9쌍을
  순서를 교대해 측정했다. hook 기대값은 모두 독립 검증을 통과했다.
- 세 번 새로 빌드한 양쪽 바이너리는 각각 원래 실험 binary hash와 일치한다.
- CPU는 기다린 자손을 포함한 user+system의 표본별 합 중앙값이다. 최대 자식
  RSS는 개별 프로세스 peak이며, 10 ms 표본 RSS 합은 공유 페이지를 중복
  계산하고 짧은 peak를 놓친다. 빌드 메모리를 횟수로 나누어 상쇄하지 않는다.

## 사전 빌드 설치 부분 비용

공식 파일은 21,958,840 bytes, 후보는 19,513,506 bytes였다. 똑같은 gzip 6
조건으로 포장한 단일 실행 파일 archive는 8,103,961 → 8,064,510 bytes다.
이는 실제 공개 전체 archive의 크기 비교가 아니다.

실제 bootstrap에서 쓰는 `shasum -a 256 -c`와 `tar -xzf`로 체크섬 검증 및
압축 해제를 실행했다. 중앙값은 252.5 → 239.6 ms, 최대 자식 RSS는 양쪽
5.75 MiB였다. 네트워크·서명·호스트 등록·기존 설치 병합은 포함하지 않는다.
Python 추출 비교도 따로 보존하지만 그 수치는 실제 installer RAM으로 읽지
않는다. 현 후보가 사전 빌드 배포의 설치 부담을 높인다는 근거는 관측하지 못했다.

## 개발자 또는 소스 설치 비용

| 지표 | 같은 컴파일러 대조군 | 후보 |
| --- | ---: | ---: |
| 빌드 시간 | 27.899 s | 30.891 s |
| 빌드 CPU | 92.082 s | 100.699 s |
| 최대 자식 RSS | 286.7 MiB | 809.5 MiB |
| 표본 RSS 합 peak | 563.1 MiB | 845.9 MiB |

추가 2.993초 및 CPU 8.617초가 들었다. 같은 소스로 빌드한 대조군/후보를
실행한 hook에서 Claude 지연 1.109 → 0.409초, CPU 1.174 → 0.435초,
Codex 지연 1.090 → 0.414초, CPU 1.159 → 0.439초였다.
이 다중 문자열 fixture를 로그 off로 순차 실행하는 조건에서 추가 빌드 시간은
5회, 추가 CPU는 12회로 상쇄된다. 수식은 `ceil(추가 빌드 비용 / hook 절감)`.
일반 사용자의 실제 손익분기나 모든 입력·캐시 상태의 결과로 일반화하지 않는다.
사전 빌드 설치에는 이 소스 빌드 비용 자체가 없다.

별도 공개 scanner 기준 비교는 Claude 1.081 → 0.405초, Codex 1.072 →
0.404초였다. `hook-control-*`와 `hook-*`를 구별한다. 처음 작성한
`tradeoff-summary.json`은 공개 scanner runtime과 재빌드 비용을 조합한 중간
계산이며 최종 손익분기는 `matched-tradeoff-summary.json`을 따른다.

## 판정

일회성 빌드 CPU·시간 증가를 반복 사용 절감으로 상쇄할 수 있는 사례는 실제로
확인했다. 다만 저메모리 환경에 사용자 소스 빌드를 요구하는 것은 별도 부담이다.
따라서 후보의 제품 채택을 다시 판단할 때 사전 빌드 배포를 유지해야 한다.
Homebrew 경로의 회귀, scanner 공급 출처·업데이트·복구·상위 유지보수 검증이
해결되지 않았으므로 기존의 전체 scanner 일괄 교체 기각 결론은 바꾸지 않는다.
설치 방식이나 호스트 계약을 깨야 한다는 근거, v4 필요성도 추가로 발견하지 못했다.


## 실제 공개 v3.7.0 bootstrap 기준 측정

별도 `public-v3.7.0-bootstrap.tar.gz`는 compiler가 없는 Ubuntu 24.04의
일회용 컨테이너 3개에 실제 공개 v3.7.0을 새로 설치한 원시 자료다. 기존 jq,
git, 공식 gitleaks가 있는 상태이며 인터넷 다운로드·체크섬·압축 해제·setup·
기본 shell integration을 포함한다. 의존성 설치, Docker 이미지 준비, Claude/
Codex 애플리케이션 등록은 측정 밖이다. 일반 컨테이너 HOME=/root를 사용했고
사용자의 실제 HOME이나 설정을 변경하지 않았다.

중앙값은 설치 1.64초, CPU 0.81초, 최대 자식 RSS 44.8 MiB였다. 표본 RSS 합은
이 설치 측정에서 수집하지 않았다. 네트워크에 영향받는 3회 기준 관측이며
미래 버전의 설치 개선율로 표현하지 않는다. 설치 후 네 플랫폼 native 자산의
체크섬과 smoke-test가 모두 통과했다. 실제 Claude/Codex 도구 dispatch가
관측됐다는 뜻은 아니다. Docker의 CgroupDriver는 none이며 외부 4 CPU/16 GiB
제한만 확인했다. 소스 빌드는 이 일반 bootstrap 과정에서 필요하지 않았다.


## 발행 후 검증 준비

이 실험 브랜치에만 public validation의 이전 버전 선택으로 3.7.0을 추가했다.
실제 공개 bootstrap bytes의 SHA-256
`a28827587c60a02c44567a480e1e0e08bf517c407f64e8b28fa4450aee75b64e`를
검증하고 고정했다. 기존 3.6.14/3.6.15 지원·pin·기대값은 유지한다.
현재 릴리스 head를 바꾸지 않고, 발행 후 이 브랜치의 workflow_dispatch로
실제 3.7.0→3.7.1 공개 다운로드·설치·업데이트와 Homebrew를 검증한다.
이 항목은 실행 준비이며, 아직 발행이나 검증 성공을 뜻하지 않는다.
