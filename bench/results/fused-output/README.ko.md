# 출력 통합 실험의 보존 증거

2026-11-05 조사 기록이다. 공개 main/release는 v3.7.1
`d00b4882c55704e5d83899ffd3820946aa9c15fa`이며, 이 성능 후보는 배포하지 않았다.
[구현 PR #403](https://github.com/JeongJaeSoon/agent-guard/pull/403)의 결과를
실패한 후보까지 덮어쓰지 않고 보존한다. `SHA256.json`은 이 디렉터리의 원시 파일 해시다.

## 비교 범위와 판정

공개 v3.7.0 archive/core, 같은 scanner bytes·설정·입력, 실제 cgroup
2CPU/1GiB/swap0 아래의 CLI 시작 비용 포함 9쌍 교대 측정이다. 각 scanner에
Claude/Codex × 21개 경로 × audit off/cold/warm을 적용한다. 사전 목표는
stdlib scanner의 다중 문자열 출력 지연 또는 CPU 10% 이상 개선이다.
모든 scanner의 일반 경로 지연·CPU 5% 초과 회귀는 허용하지 않는다.
실제 Homebrew 설치는 stdlib 소스 재빌드와 구분한다.

- `ci-b673546/`: 후보에만 편의 wrapper가 있던 첫 측정. 일반 경로 5% 회귀
  기준 미달, fixture PATH 누락 및 native 준비 경로의 기존 fault injection
  미적용도 보존했다. 후속 수정은 CLI 직접 실행·fixture 도구 분리·원래 기대값
  유지로 처리했고 시간 제한을 늘리지 않았다.
- `ci-733cf38/`: 양쪽 CLI 직접 실행. stdlib 126개 비교에서 목표 지연
  14.8~17.0%, CPU 12.6~15.5% 감소, 일반 경로 기준 통과. 공식 scanner 목표
  개선은 약 4~5%이며 warm Claude pre-read-placeholder가 지연 +6.06% /
  CPU +5.42%여서 **전체 실패**다. Homebrew는 build-info 검증기에서 중단돼
  측정값이 없다. 총 252개 비교의 독립 기대값 불일치는 0이다.
- 후속 `afab414`는 출력 함수 정의를 출력 경로에서만 읽도록 분리했다.
  원래 실패를 보존하고 새 구현을 측정했다. **378개 비교 / 6804회 CLI 실행에서
  독립 기대값 불일치 0, 일반 경로 5% 초과 회귀 0이며 사전 성능 기준을 통과했다.**
  전체 재작성 없이 목표 경로의 이득은 증명했지만 Intel의 기존 거대 numeric
  fallback 시간 실패가 남아 이 사실만으로 배포 적합성을 선언하지 않는다.

| `afab414` 동일 scanner 내 목표 경로 | 지연 감소 | CPU 감소 |
|---|---:|---:|
| 공식 공개 scanner | 4.65~7.13% | 4.25~7.51% |
| 동일 upstream stdlib 비교 빌드 | 13.63~16.73% | 11.08~15.04% |
| 실제 Homebrew 설치 바이너리 | 15.71~16.72% | 14.17~15.08% |

각 범위는 두 호스트 × audit 세 상태의 결과이며 scanner 간 속도 비율이 아니다.
공식 scanner의 10% 개선이나 모든 사용자 작업의 같은 개선율을 주장하지 않는다.
원시 자료는 `ci-afab414/`, 재집계 결과는 그 디렉터리의 `summary.json`이다.

CPU는 각 실행의 user+system 합 중앙값이며 사용률이 아니다. 최대 자식 RSS는
동시 프로세스 전체 메모리가 아니다. 표본 RSS 합은 10ms 간격으로 공유 페이지를
중복 집계할 수 있고 짧은 피크를 놓칠 수 있다.

`733cf38`의 부하 측정은 Claude에서 8요청 × 3회 중앙값이다. 이 head는 위의 회귀로 기각했으므로
아래 수치를 채택·배포 성과로 읽지 않는다.

|---|---:|---:|---:|---:|
| stdlib / 1 | 3.73→4.43 | 2.37→2.02 | 37.23→37.16 | 58.61→63.76 |

| 공식 / 4 | 1.97→2.00 | 8.04→7.96 | 64.42→64.42 | 301.42→319.82 |

시간·CPU 이득이 메모리 감소를 뜻하지 않는다. 표본 합은 오히려 증가한 경우가 있다.

성능 기준을 통과한 `afab414`에서 Claude와 실제 Homebrew의 1개/4개 동시 요청 처리량은
각각 3.62→4.40 / 4.38→5.16 req/s였다. 8요청 CPU는 2.44→2.03 /
3.66→3.09초, 최대 자식 RSS는 39.25→39.30 / 39.67→39.56MiB였다.
표본 RSS 합은 60.75→66.20 / 215.30→236.54MiB로 늘었다. 즉 이 후보의
주된 이득은 지연·CPU·처리량이며 **전체 실행 메모리 감소는 입증되지 않았다.**

## 정확도와 Intel 실패

고정된 `355bf54`의 전체 suite는 컴파일러 없는 격리 Linux 컨테이너에서
2727 성공/0 실패, exit 0이었다. 런타임은 `733cf38`과 같다. 후속 지연 로딩은
부분 쓰기·helper 누락·모듈 누락의 두 호스트 6건을 통과했다. 출력 탐지나
whole-leaf 기대값을 완화하지 않았다.

`733cf38`의 Linux x64/ARM과 macOS ARM 출력 suite는 통과했지만 Intel은
1042 성공/1 실패다. 960000개 숫자/불리언 fallback이 36초여서 원래 20초 조건을
초과했다. 후속 독립 진단에서 공개 3.7.0/3.7.1/후보 모두 약 37~48초로 재현했고
전체 출력은 독립 기대값과 일치했다. 계측 wrapper 자체의 큰 인자 복사 비용 때문에
계측 시간을 원본 성능으로 사용하지 않는다. 별도 수정에서는 항등 문자열 변환과
awk 스칼라 레코드의 중복 구조 검사를 줄이고, 같은 20초 기준과 추가 독립 fixture를
검증한다. 최초 배포 후 host 출력 불일치와 같은 원인이라고 확정하지 않는다.

숫자 fallback의 첫 별도 수정은 Intel 21.8초, 인자 전달을 추가로 줄인 수정은
24.5초, 조기 cap 검사를 적용한 수정은 25.2초로 모두 20초 기준 미달이었다.
네 플랫폼의 출력은 독립 기대값에 맞았지만 이를 시간 문제의 해결로 취급하지
않는다. 첫 수정의 전체 suite 2739건, 두 번째 수정의 출력 suite 1051건은
격리 Linux에서 각각 0 실패로 끝났다. 다음 진단은 동일 코드의 locale 대조와
awk/jq 자식 CPU를 분리한다. 실패가 사라질 때까지 같은 코드를 재시도하지 않는다.

실패를 정상 치환으로 인정하지 않으며, 이 실패를 지우기 위한 CI 재실행도 하지 않는다.

## 거대 숫자 fallback의 별도 수정과 한계

실패한 21.8초(`9c5d937`), 24.5초(`e87a903`), 25.2초(`a7b7c55`) 원시를
모두 보존했다. 같은 a7 코드의 locale 대조 `06e775d`는 Intel 기본 UTF-8에서
47.9초, C에서 9.6초였다. awk 자체 CPU는 양쪽 약 4~5초라서 전체 차이를
설명하지 못했다. 단일 진단 표본을 채택 성능 비율로 쓰지 않는다.

함수 앞의 임시 `LC_ALL=C` 후보(`89aa36c`)도 Intel 58.6초로 실패했다.
명시적인 shell locale 대입과 이전 값/set-unset 복원(`88cc1ab`)에서는
Claude 독립 출력과 원래 20초 조건이 네 플랫폼에서 통과했다. Linux x64
1.43초, ARM 1.18초, macOS ARM 5.24초, Intel 11.12초였다. 같은 CLI bytes의
추가 Codex 진단(`fe6eae4`)은 각각 1.69초, 1.50초, 4.68초, 19.66초였다.
Intel Codex는 한계에 가까우므로 충분한 시간 여유가 있다고 주장하지 않는다.
호출 전후 locale 상태도 확인했다. 이 수정은 문자열 없는 상한 초과 ASCII JSON에
한정하며 기존 cap·보수적 치환·구조/숫자 독립 기대값을 유지한다.

통합 head `bd19cb5`의 CLI SHA-256은 위 성공한 두 호스트 진단과 같은
`f33a9add5f9ae7f25c9e68ac876448f08adddcea245088a639bdb11b29d2da4d`다.
이 numeric 문제와 scanner readiness timeout, 최초 자료 없는 host mismatch는
서로 구분한다. 현재 공개 배포는 여전히 v3.7.1이며 새 후보를 발행하지 않았다.
호환성 변경이나 v4.0.0 필요성도 입증되지 않았다.

## 후속 readiness 진단과 재현 가능한 타이머 경합

`d69bffa`의 macOS Intel/ARM 독립 진단은 각 24회 hook(원본/계측 ×
GOMAXPROCS 기본/1 × 6라운드), 12회 직접 version, 2회 inittrace다.
모든 합성 fixture의 독립 기대값은 맞았고 readiness timeout은 재현되지 않았다.
Intel 직접 version은 0.34~0.83초, inittrace의 go-re2 초기화는 약 0.28~0.31초였다.
이 진단의 성공은 실패한 `bd19cb5` CI를 대체하거나 원인 해결을 뜻하지 않는다.
초기 진단 `0485b39`는 중복 계측 anchor assertion에서 중단됐다. 제품 실행 전의
진단기 결함이며 실패 artifact와 로그도 `ci-readiness-0485b39/`에 보존했다.

별도 `c1c7990`에서 부모가 완료된 version 자식을 reap한 직후 3초 동안
지연되는 상황을 의도적으로 만들었다. 기존 코드의 정상 종료와 exit 7은 모두
잘못된 timeout으로 바뀌었고, 실제 8초 걸리는 자식만 기대대로 timeout이었다
(1성공/2실패). watchdog이 timeout을 기록하기 전에 자식의 생존 여부를 확인하는
최소 수정은 세 경우를 모두 통과했다. 원래 2초 제한을 늘리지 않았고, 기존
readiness 47개 검사도 모두 통과했다. 네 플랫폼 전후 회귀 실행 `42026053383`에서도 각각 기존 1성공/2실패,
수정 3성공/0실패, 기존 readiness 47성공/0실패를 확인했다.
이 결정적 경합 재현을 최초 자료 없는 mismatch나 앞선 실제 CI timeout의
근본 원인으로 확정하지 않는다.

읽기 전용 `bd19cb5` 소스와 helper로 수행한 컴파일러 없는 격리 Linux 전체 suite는
2739 성공/0실패였고 Docker die event의 exitCode도 0이었다. 전체 로그와 종료
이벤트 메타데이터를 보존했다. 이는 새 타이머 수정이나 네 플랫폼 설치 검증의
완료를 의미하지 않는다.

## 설치 비용: 같은 컴파일러와 실험 payload

`install-cost-afab414/`는 **Linux x64 로컬 4CPU/16GiB**의 별도 측정이다.
CI의 2CPU/1GiB 성능 결과와 섞지 않는다. Rust 1.85.0, 동일 GNU target,
의존 소스 캐시는 준비된 상태, 매 표본 빈 target, offline/locked 빌드 3쌍이다.
공개 redactor를 그대로 두고 별도 prepare helper를 넣은 격리 실험 payload를
같은 gzip 설정으로 만들었다. 현재 이 payload는 공개 설치물이나 네 플랫폼 배포물이 아니다.

| 지표 | 기준 | 후보 |
|---|---:|---:|
| core 개발자 빌드 시간 | 8.727초 | 8.783초 |
| 빌드 CPU 합 | 11.379초 | 11.432초 |
| 빌드 최대 자식 RSS | 293.74MiB | 293.85MiB |
| 빌드 표본 RSS 합 | 645.91MiB | 570.61MiB |
| 동일 형식 압축 크기 | 1,922,701 bytes | 2,151,798 bytes |
| 설치 payload 크기 | 3,494,569 bytes | 3,954,536 bytes |
| 체크섬+압축 해제 시간, 7쌍 | 103.8ms | 110.0ms |
| 체크섬+압축 해제 CPU | 103.6ms | 109.6ms |
| 체크섬+압축 해제 최대 자식 RSS | 15.125MiB | 15.250MiB |

같은 컴파일러/target에서 core 단일 파일은 444,840→453,032 bytes였다.
현재 실험은 공개 redactor와 prepare를 분리하므로 전체 payload에는 helper 전부가
추가된다. 단일 core로 합칠 때의 최종 배포 크기로 주장하지 않는다. 빌드 표본 RSS 합의
차이도 작은 표본·컴파일 병렬 실행 시점의 영향을 받으므로 메모리 개선으로 채택하지 않는다.

이 측정은 Rust toolchain 설치·의존 다운로드·네트워크·Claude/Codex 등록을 포함하지
않는다. 사전 빌드 파일을 배포하면 사용자에게 컴파일 비용을 요구할 필요가 없다.
source-only 사용자가 새 helper를 직접 빌드하는 선택을 한다면 0.057초의 빌드 차이가
아니라 후보 전체 8.783초/CPU 11.432초를 추가 지불한다. 이 구분 없이 손익을 계산하지 않는다.

같은 로컬 payload/helper로 실행한 별도 9쌍 예비 사용 비교는 공식 scanner의
다중 문자열 지연 1.046→0.988초, CPU 1.107→1.051초, stdlib은
0.354→0.273초, CPU 0.382→0.302초였다. 해당 stdlib 작업만 반복한다는 조건에서
새 helper 전체 빌드 비용은 대략 지연 110회/CPU 142회로 상쇄된다. 단순 압축 해제의
추가 6ms는 한 번의 해당 작업 절감보다 작지만 **다운로드 시간은 이 계산에 없다**.
메모리 피크는 반복 사용으로 상쇄되지 않는다. 이 예비 비교는 전체 일반 경로 기준이나
네 플랫폼 채택 검증을 대신하지 않는다.

원시 측정과 재집계 스크립트를 함께 보존하며 공개 v3.7.1의 설치/업데이트 검증은
[별도 배포 보고서](https://github.com/JeongJaeSoon/agent-guard/blob/d58823b8055972a589e7a9cf4752dab27cc857d6/bench/results/release-validation/v3.7.1-report.ko.md)를 참조한다.

추가로 실제 CI 빌드 core 자체의 파일 크기를 공개 v3.7.0과 대조했다
(`prebuilt-size-bd19.json`). Linux x64와 macOS Intel은 각각 +4096 bytes,
ARM 두 플랫폼은 파일 크기가 같았다. prepare 명령을 기존 core와 함께 담으면
별도 helper 파일을 영구적으로 더 설치할 필요는 없다. 따라서 위 합성 별도-helper
패키지의 +229097 bytes를 최종 제품 설치 증가분으로 확정하지 않는다. 이 실제
산출물 크기 대조도 Intel qualification이 실패한 후보의 값이며, 공개 릴리스나
최종 설치 시간 검증은 아니다.

## 실제 공유 설치 core 첫 후보 ae18024: 일반 경로 기준 초과로 기각

같은 공개 v3.7.0, 실제 동일 scanner·설정·입력, 2 CPU/1 GiB/swap 0, 9쌍 교대 반복의 252개 비교(4,536회 CLI 측정)는 불일치 0이었습니다. 후속 독립 브랜치 `codex/startup-path-proof`의 94f97ca는 절대 경로의 일반 실행 파일에서 기존 subshell 내장 경로 처리로 자식 두 개를 줄입니다. 상대·심볼릭 링크 경로는 기존 resolver를 사용하며 8개 독립 위치 계약을 추가했습니다. 로컬 9쌍 직접 비교에서 pre-read-clean 지연 72.873→67.736 ms, CPU 77.249→73.241 ms, pre-unknown-tool 지연 53.859→52.489 ms, CPU 59.042→58.793 ms였습니다. 프로세스 생성은 각각 51→49, 37→35이며 scanner 준비 확인은 양쪽 1회입니다. 두 경로의 불일치는 0입니다. 로컬 외부 cgroup 4 CPU/16 GiB이고 비교 scanner 빌드이므로 실제 Homebrew 정식 관문을 대신하지 않습니다.

## 두 번째 릴리스 후보 2ee4ae6: 공유 core 통과, 기본 exec 관문 실패

`2ee4ae6c3818157a5f8f25c1ac8dbeb63a3fb723`의 별도 기여도 분리 378개와 실제 공유 core 252개 비교는 독립 출력 불일치 0, 일반 경로 지연/CPU 5% 초과 회귀 0이었다. 공유 core Homebrew 목표는 10% 이상 개선했고 네 플랫폼 실행·설치·공유 core 복귀 계약도 통과했다. 원본 ZIP·요약·정확한 head의 checks는 `ci-2ee4ae6/`, `ci-2ee4ae6-native/`에 보존했다.

그러나 기존 별도 `Packaged performance evidence`는 실패했다(run 42039910187, job 127298190545). 기존 pre-native Git 기준 `9a0ee9e`의 셸과 현재 기본 packaged 경로를 같은 공식 scanner로 비교한 `exec-long-quoted-secret`의 지연이 0.982542939→1.035507471초(+5.3906%), CPU +4.2106%였다. 출력은 독립 기대값과 일치했다. 새 공유 core 관문이 통과했다는 이유로 기존 실패를 무시하지 않고 이 head의 병합·발행을 보류했다. 제한·기대값·실패 상태를 바꾸거나 같은 코드로 재실행하지 않았다.

### 실제 비용 분리와 구간 처리 수정

독립 브랜치 `codex/plaintext-frame-span`의 `2a03f38`에서 plaintext framing의 이스케이프 없는 구간을 한 번에 이어붙이도록 바꿨다. 기존 바이트별 반복 복사를 줄이며 이스케이프가 있는 행은 원래 상태 기계로 처리한다. 60KB 다중행·여러 레코드·RS/US 이스케이프·문맥 경계·최장 일치·비 UTF-8 바이트·빈 입력의 독립 기대값 10개를 추가해 통과했다. scanner·탐지·마스킹 범위·정책은 바꾸지 않았다.

로컬 9쌍 교대 측정에서 해당 단계 지연은 60.797543→6.414322ms, CPU는 58.772→7.233ms였다. 전체 CLI의 긴 quoted secret은 지연 485.003196→439.146605ms(-9.4549%), CPU 519.494→471.814ms(-9.1782%)였다. exec-multiline은 지연 +1.3478%/CPU +2.0506%, exec-clean은 -1.2738%/-3.4212%였다. 모든 독립 기대값이 일치했다. 로컬 4CPU/16GiB·stdlib 비교 scanner의 진단이며 공식 2CPU/1GiB 성능 판정을 대신하지 않는다. 스크립트·입력·표본·요약은 frame-span ZIP 두 개에 보존했다.

기존 packaged 관문을 그대로 유지하고 실제 공개 v3.7.0을 기준으로 기본 exec 세 경로와 unknown-tool을 9쌍 비교하는 추가 지연/CPU 5% 관문도 넣었다. 새 릴리스 head는 `10cc80c89d6c616616ce2a3642c0e362bdec52ba`이며 이 기록 시점 CI 진행 중이다. 설치 비용은 앞선 사전 발행 후보 측정이며 최종 공개 자산에서 재확인해야 한다. 공개 최신은 v3.7.1이다.

앞선 startup 수정의 로컬 전체 suite는 2625통과/0실패였으나 컨테이너 UID 때문에 실제 scanner optional 블록과 Node/zsh/ACL 등이 생략되었다. Git archive도 worktree 메타데이터가 컨테이너 밖에 있어 생략되었다. 로그·종료 상태·최초 mount 권한 오류를 모두 보존하며 이것을 실제 scanner 통합 완료로 과장하지 않는다. 새 구간 처리 전체 검사는 읽을 수 있는 실제 scanner와 독립 Git clone을 사용한다.
