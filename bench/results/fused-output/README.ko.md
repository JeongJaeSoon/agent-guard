# 출력 통합 실험의 보존 증거

2026-11-05 조사 기록이다. 공개 main/release는 v3.7.1
`d00b4882c55704e5d83899ffd3820946aa9c15fa`이며, 이 성능 후보는 배포하지 않았다.
[구현 PR #403](https://github.com/JeongJaeSoon/agent-guard/pull/403)의 결과를
실패한 후보까지 덮어쓰지 않고 보존한다. `SHA256.json`은 이 디렉터리의 원시 파일 해시다.

## 비교 범위와 판정

공개 v3.7.0 archive/core, 같은 scanner bytes·설정·입력, 실제 cgroup
2CPU/1GiB/swap0 아래의 CLI 시작 비용 포함 9쌍 교대 측정이다. 각 scanner에
Claude/Codex × 21개 경로 × audit off/cold/warm을 적용한다. 사전 목표는
stdlib scanner의 다중 문자열 출력 지연 또는 CPU 10% 이상 개선이다.
모든 scanner의 일반 경로 지연·CPU 5% 초과 회귀는 허용하지 않는다.
실제 Homebrew 설치는 stdlib 소스 재빌드와 구분한다.

- `ci-b673546/`: 후보에만 편의 wrapper가 있던 첫 측정. 일반 경로 5% 회귀
  기준 미달, fixture PATH 누락 및 native 준비 경로의 기존 fault injection
  미적용도 보존했다. 후속 수정은 CLI 직접 실행·fixture 도구 분리·원래 기대값
  유지로 처리했고 시간 제한을 늘리지 않았다.
- `ci-733cf38/`: 양쪽 CLI 직접 실행. stdlib 126개 비교에서 목표 지연
  14.8~17.0%, CPU 12.6~15.5% 감소, 일반 경로 기준 통과. 공식 scanner 목표
  개선은 약 4~5%이며 warm Claude pre-read-placeholder가 지연 +6.06% /
  CPU +5.42%여서 **전체 실패**다. Homebrew는 build-info 검증기에서 중단돼
  측정값이 없다. 총 252개 비교의 독립 기대값 불일치는 0이다.
- 후속 `afab414`는 출력 함수 정의를 출력 경로에서만 읽도록 분리했다.
  원래 실패를 보존하고 새 구현을 측정했다. **378개 비교 / 6804회 CLI 실행에서
  독립 기대값 불일치 0, 일반 경로 5% 초과 회귀 0이며 사전 성능 기준을 통과했다.**
  전체 재작성 없이 목표 경로의 이득은 증명했지만 Intel의 기존 거대 numeric
  fallback 시간 실패가 남아 이 사실만으로 배포 적합성을 선언하지 않는다.

| `afab414` 동일 scanner 내 목표 경로 | 지연 감소 | CPU 감소 |
|---|---:|---:|
| 공식 공개 scanner | 4.65~7.13% | 4.25~7.51% |
| 동일 upstream stdlib 비교 빌드 | 13.63~16.73% | 11.08~15.04% |
| 실제 Homebrew 설치 바이너리 | 15.71~16.72% | 14.17~15.08% |

각 범위는 두 호스트 × audit 세 상태의 결과이며 scanner 간 속도 비율이 아니다.
공식 scanner의 10% 개선이나 모든 사용자 작업의 같은 개선율을 주장하지 않는다.
원시 자료는 `ci-afab414/`, 재집계 결과는 그 디렉터리의 `summary.json`이다.

CPU는 각 실행의 user+system 합 중앙값이며 사용률이 아니다. 최대 자식 RSS는
동시 프로세스 전체 메모리가 아니다. 표본 RSS 합은 10ms 간격으로 공유 페이지를
중복 집계할 수 있고 짧은 피크를 놓칠 수 있다.

`733cf38`의 부하 측정은 8요청 × 3회 중앙값이다. 이 head는 위의 회귀로 기각했으므로
아래 수치를 채택·배포 성과로 읽지 않는다.

| scanner / 동시성 | 처리량 req/s 이전→후보 | CPU 초/8요청 이전→후보 | 최대 자식 RSS MiB | 표본 RSS 합 MiB |
|---|---:|---:|---:|---:|
| stdlib / 1 | 3.73→4.43 | 2.37→2.02 | 37.23→37.16 | 58.61→63.76 |
| stdlib / 4 | 4.48→5.25 | 3.63→3.04 | 37.65→37.68 | 207.40→226.37 |
| 공식 / 1 | 1.63→1.72 | 5.13→4.90 | 63.29→63.24 | 84.57→88.64 |
| 공식 / 4 | 1.97→2.00 | 8.04→7.96 | 64.42→64.42 | 301.42→319.82 |

시간·CPU 이득이 메모리 감소를 뜻하지 않는다. 표본 합은 오히려 증가한 경우가 있다.

성능 기준을 통과한 `afab414`에서 실제 Homebrew의 1개/4개 동시 요청 처리량은
각각 3.62→4.40 / 4.38→5.16 req/s였다. 8요청 CPU는 2.44→2.03 /
3.66→3.09초, 최대 자식 RSS는 39.25→39.30 / 39.67→39.56MiB였다.
표본 RSS 합은 60.75→66.20 / 215.30→236.54MiB로 늘었다. 즉 이 후보의
주된 이득은 지연·CPU·처리량이며 **전체 실행 메모리 감소는 입증되지 않았다.**

## 정확도와 Intel 실패

고정된 `355bf54`의 전체 suite는 컴파일러 없는 격리 Linux 컨테이너에서
2727 성공/0 실패, exit 0이었다. 런타임은 `733cf38`과 같다. 후속 지연 로딩은
부분 쓰기·helper 누락·모듈 누락의 두 호스트 6건을 통과했다. 출력 탐지나
whole-leaf 기대값을 완화하지 않았다.

`733cf38`의 Linux x64/ARM과 macOS ARM 출력 suite는 통과했지만 Intel은
1042 성공/1 실패다. 960000개 숫자/불리언 fallback이 36초여서 원래 20초 조건을
초과했다. 후속 독립 진단에서 공개 3.7.0/3.7.1/후보 모두 약 37~48초로 재현했고
전체 출력은 독립 기대값과 일치했다. 계측 wrapper 자체의 큰 인자 복사 비용 때문에
계측 시간을 원본 성능으로 사용하지 않는다. 별도 수정에서는 항등 문자열 변환과
awk 스칼라 레코드의 중복 구조 검사를 줄이고, 같은 20초 기준과 추가 독립 fixture를
검증한다. 최초 배포 후 host 출력 불일치와 같은 원인이라고 확정하지 않는다.

숫자 fallback의 첫 별도 수정은 Intel 21.8초, 인자 전달을 추가로 줄인 수정은
24.5초, 조기 cap 검사를 적용한 수정은 25.2초로 모두 20초 기준 미달이었다.
네 플랫폼의 출력은 독립 기대값에 맞았지만 이를 시간 문제의 해결로 취급하지
않는다. 첫 수정의 전체 suite 2739건, 두 번째 수정의 출력 suite 1051건은
격리 Linux에서 각각 0 실패로 끝났다. 다음 진단은 동일 코드의 locale 대조와
awk/jq 자식 CPU를 분리한다. 실패가 사라질 때까지 같은 코드를 재시도하지 않는다.

## 설치 비용: 같은 컴파일러와 실험 payload

`install-cost-afab414/`는 **Linux x64 로컬 4CPU/16GiB**의 별도 측정이다.
CI의 2CPU/1GiB 성능 결과와 섞지 않는다. Rust 1.85.0, 동일 GNU target,
의존 소스 캐시는 준비된 상태, 매 표본 빈 target, offline/locked 빌드 3쌍이다.
공개 redactor를 그대로 두고 별도 prepare helper를 넣은 격리 실험 payload를
같은 gzip 설정으로 만들었다. 현재 이 payload는 공개 설치물이나 네 플랫폼 배포물이 아니다.

| 지표 | 기준 | 후보 |
|---|---:|---:|
| core 개발자 빌드 시간 | 8.727초 | 8.783초 |
| 빌드 CPU 합 | 11.379초 | 11.432초 |
| 빌드 최대 자식 RSS | 293.74MiB | 293.85MiB |
| 빌드 표본 RSS 합 | 645.91MiB | 570.61MiB |
| 동일 형식 압축 크기 | 1,922,701 bytes | 2,151,798 bytes |
| 설치 payload 크기 | 3,494,569 bytes | 3,954,536 bytes |
| 체크섬+압축 해제 시간, 7쌍 | 103.8ms | 110.0ms |
| 체크섬+압축 해제 CPU | 103.6ms | 109.6ms |
| 체크섬+압축 해제 최대 자식 RSS | 15.125MiB | 15.250MiB |

같은 컴파일러/target에서 core 단일 파일은 444,840→453,032 bytes였다.
현재 실험은 공개 redactor와 prepare를 분리하므로 전체 payload에는 helper 전부가
추가된다. 단일 core로 합칠 때의 최종 배포 크기로 주장하지 않는다. 빌드 표본 RSS 합의
차이도 작은 표본·컴파일 병렬 실행 시점의 영향을 받으므로 메모리 개선으로 채택하지 않는다.

이 측정은 Rust toolchain 설치·의존 다운로드·네트워크·Claude/Codex 등록을 포함하지
않는다. 사전 빌드 파일을 배포하면 사용자에게 컴파일 비용을 요구할 필요가 없다.
source-only 사용자가 새 helper를 직접 빌드하는 선택을 한다면 0.057초의 빌드 차이가
아니라 후보 전체 8.783초/CPU 11.432초를 추가 지불한다. 이 구분 없이 손익을 계산하지 않는다.

같은 로컬 payload/helper로 실행한 별도 9쌍 예비 사용 비교는 공식 scanner의
다중 문자열 지연 1.046→0.988초, CPU 1.107→1.051초, stdlib은
0.354→0.273초, CPU 0.382→0.302초였다. 해당 stdlib 작업만 반복한다는 조건에서
새 helper 전체 빌드 비용은 대략 지연 110회/CPU 142회로 상쇄된다. 단순 압축 해제의
추가 6ms는 한 번의 해당 작업 절감보다 작지만 **다운로드 시간은 이 계산에 없다**.
메모리 피크는 반복 사용으로 상쇄되지 않는다. 이 예비 비교는 전체 일반 경로 기준이나
네 플랫폼 채택 검증을 대신하지 않는다.

원시 측정과 재집계 스크립트를 함께 보존하며 공개 v3.7.1의 설치/업데이트 검증은
[별도 배포 보고서](https://github.com/JeongJaeSoon/agent-guard/blob/d58823b8055972a589e7a9cf4752dab27cc857d6/bench/results/release-validation/v3.7.1-report.ko.md)를 참조한다.
