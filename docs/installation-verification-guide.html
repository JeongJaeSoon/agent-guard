Agent Guard operations guide

설치·업데이트·동작 확인 가이드

Agent Guard 3.1.1을 standalone CLI, Homebrew, Claude Code, Codex, Git hook, GitHub Actions에 설치하고 “설치됨”이 아니라 “실제로 보호됨”까지 확인하는 운영 절차서입니다.

1. 현재 구현·릴리즈 상태

결론: 요청한 핵심 코드는 main에 반영됐고 v3.1.1로 공개됐습니다. 다만 host plugin은 바이너리 검증만으로 활성화됐다고 판단하지 않습니다. Claude와 Codex 각각에서 설치·reload/restart와 live hook probe를 통과해야 해당 host의 설치가 완료됩니다.
항목상태확인 기준
저장소 반영완료핵심 기능 b38b4ab과 v3.1.1 release commit b1d168e가 main에 포함
CLI·manifest 버전완료CLI, Claude manifest, Codex manifest, marketplace가 모두 3.1.1
GitHub Release완료v3.1.1 release에 tarball, SHA-256, formula, bootstrap, installer 게시
로컬 바이너리통과doctor와 smoke-test 성공, gitleaks 8.30.1 확인
CI통과Ubuntu·macOS·ShellCheck·actionlint·plugin validation·scanner workflow 성공
Homebrew formula공개·실설치 검증jeongjaesoon/tap 게시, 공개 tap 설치와 brew test, wrapper recursion 방지 확인
Claude/Codex live hookhost별 확인 필요각 머신에서 plugin 설치 후 이 문서의 live probe를 실행

이 표의 “바이너리 통과”는 host가 hook을 실제 호출한다는 뜻이 아닙니다. Agent Guard는 보호 대상 경계마다 별도 증거를 요구합니다.

3. 공통 사전 조건과 검증 레벨

필수 런타임

  • sh, awk, git
  • jq
  • gitleaks 8.30.0 이상, 8.30.1 권장
  • release 다운로드 설치에는 curl, tar, shasum, ln

검증 4단계

  1. Identity: 예상한 binary와 version인가
  2. Health: dependency·policy가 준비됐는가
  3. Behavior: clean allow와 synthetic leak block이 모두 되는가
  4. Dispatch: 현재 host/tool route가 hook을 실제 호출하는가

공통 진단 명령

command -v agent-guard
agent-guard version
agent-guard doctor
agent-guard check
agent-guard smoke-test
명령/scan 종료 코드의미판정
0검사 실행 및 clean통과
1secret 발견의도한 negative probe면 통과, 실제 작업이면 차단
3검사를 실행하지 못함clean으로 취급 금지
기타 non-zeroscanner 또는 사용법 오류원인 해결 후 재검증

Hook 경계의 인프라 오류는 AGENT_GUARD_INFRA_FAILURE_MODE로 제어합니다. 기본 open은 세션당 한 번 경고 후 계속하며, closed는 차단합니다. 실제 secret 탐지는 설정과 무관하게 항상 차단됩니다.

4. Standalone CLI

clone 없이 설치하거나 Homebrew를 쓰지 않는 Linux 환경에 적합합니다. 설치본은 기본적으로 ~/.agent-guard, 실행 링크는 ~/.local/bin/agent-guard에 둡니다.

1

bootstrap을 파일로 받은 뒤 실행

짧은 설치가 필요하면 README의 pipe 방식도 지원하지만, 운영 환경에서는 다운로드·문법 확인·실행을 분리하면 실패 지점을 보기 쉽습니다.

ag_tmp="$(mktemp -d)"
curl -fsSL \
  https://github.com/JeongJaeSoon/agent-guard/releases/latest/download/bootstrap.sh \
  -o "$ag_tmp/bootstrap.sh"
sh -n "$ag_tmp/bootstrap.sh"
AGENT_GUARD_VERSION=3.1.1 sh "$ag_tmp/bootstrap.sh"
2

PATH와 기본 동작 확인

export PATH="$HOME/.local/bin:$PATH"
agent-guard version
agent-guard doctor
agent-guard smoke-test

예상 version은 agent-guard 3.1.1입니다. doctor는 jq·git·gitleaks를 모두 ok로 표시해야 합니다.

3

업데이트

agent-guard update
agent-guard version
agent-guard doctor
agent-guard smoke-test

update는 standalone 설치 전용입니다. Plugin cache에서 실행하면 host plugin manager로 업데이트하라는 오류가 정상입니다.

설치 위치나 shell wrapping을 바꾸고 싶을 때 
AGENT_GUARD_HOME="$HOME/.local/share/agent-guard" \
AGENT_GUARD_BIN_DIR="$HOME/.local/bin" \
AGENT_GUARD_COMMAND_WRAPPING=off \
AGENT_GUARD_VERSION=3.1.1 \
sh "$ag_tmp/bootstrap.sh"

AGENT_GUARD_COMMAND_WRAPPING=off는 shell integration을 설치하되 command wrapping은 끕니다.

5. Homebrew

macOS에서 CLI version과 업데이트를 Homebrew가 소유하게 하는 권장 경로입니다. Formula는 release tarball의 고정 SHA-256을 사용하고, libexec 안의 실제 binary를 호출하는 얇은 wrapper만 bin에 둡니다.

1

tap 및 설치

brew tap JeongJaeSoon/tap
brew trust --formula jeongjaesoon/tap/agent-guard
brew install JeongJaeSoon/tap/agent-guard
Homebrew 6: third-party tap trust가 필수이므로 전체 tap보다 범위가 좁은 formula 단위 trust를 권장합니다. Release asset의 agent-guard.rb만 내려받아 brew install /tmp/agent-guard.rb로 설치하는 방식은 지원되지 않습니다.
2

Formula와 실제 binary 확인

brew info JeongJaeSoon/tap/agent-guard
brew test JeongJaeSoon/tap/agent-guard
command -v agent-guard
agent-guard version
agent-guard doctor
agent-guard smoke-test

brew test가 version 문자열을 확인합니다. agent-guard version이 즉시 끝나지 않고 반복 호출되면 wrapper recursion 결함이므로 설치 성공으로 보지 않습니다.

3

업데이트와 rollback

brew update
brew upgrade JeongJaeSoon/tap/agent-guard
agent-guard version
agent-guard smoke-test

업데이트 문제가 있으면 먼저 brew info에서 설치/최신 version을 비교합니다. Formula를 임의로 고치기보다 tap의 이전 정상 commit 또는 이전 formula version으로 되돌리는 PR을 사용합니다.

6. Claude Code plugin

경계: Claude plugin 설치본은 보통 agent-guard를 shell PATH에 추가하지 않습니다. 진단은 plugin-local binary 또는 /agent-guard:setup-agent-guard를 사용합니다.
1

Marketplace와 plugin 설치

Claude Code 안에서:

/plugin marketplace add JeongJaeSoon/agent-guard
/plugin install agent-guard@agent-guard
/reload-plugins

또는 터미널에서:

claude plugin marketplace add JeongJaeSoon/agent-guard
claude plugin install agent-guard@agent-guard --scope user
claude plugin list
2

Dependency 및 plugin-local smoke

/agent-guard:setup-agent-guard

Skill이 안내한 plugin-local 실행 파일로 check와 smoke-test가 모두 통과해야 합니다. macOS에서 dependency가 없다면 승인 후 brew install jq gitleaks를 사용할 수 있습니다.

3

Bash tool의 live hook dispatch 확인

Claude에게 다음 명령을 일반 Bash tool로 실행하라고 요청합니다.

printf '%s\n' 'AGENT_GUARD_LIVE_PRE_TOOL_PROBE'

성공 신호: marker가 출력되기 전에 Agent Guard가 차단합니다.

printf '%s\n' 'AGENT_GUARD_LIVE_POST_TOOL_PROBE'

성공 신호: raw marker가 모델에 도달하지 않고 [REDACTED] 또는 sanitized replacement로 보입니다.

4

선택: ! shell escape 보호

/agent-guard:setup-shell

shell rc가 갱신되므로 새 shell과 Claude Code를 다시 시작합니다. 이후 비대화형 출력 명령은 !agx <command>로 실행합니다. Fish에서는 자동 function 설치가 되지 않으므로 setup 출력의 고정 executable 경로를 사용합니다.

5

업데이트

claude plugin marketplace update agent-guard
claude plugin update agent-guard@agent-guard --scope user
claude plugin list

Claude Code에서 /reload-plugins를 실행하고 새 세션에서 setup과 두 live probe를 반복합니다. Shell integration version drift 경고가 있으면 /agent-guard:setup-shell을 다시 실행합니다.

7. Codex plugin

공식 OpenAI 문서 기준으로 Codex CLI에서는 /plugins에서 plugin을 설치하고, 설치 후 새 세션을 시작해야 bundled skill/tool을 사용할 수 있습니다. IDE extension은 plugin을 지원하지 않으므로 Codex CLI 또는 ChatGPT desktop의 Codex surface를 사용합니다.

1

Marketplace 등록과 plugin 설치

codex plugin marketplace add JeongJaeSoon/agent-guard
codex plugin list --marketplace agent-guard
codex plugin add agent-guard@agent-guard

대화형 Codex에서는 /plugins를 열고 Agent Guard를 선택해도 됩니다. 설치 후 반드시 새 Codex 세션을 시작합니다.

2

Hook trust 검토

Settings > Hooks에서 Agent Guard의 다음 hook을 각각 검토하고 trust/enable 합니다.

  • SessionStart
  • UserPromptSubmit
  • PreToolUse
  • PostToolUse
  • Stop

Untrusted 또는 Modified는 비활성으로 취급합니다. hooks.state나 trust hash를 직접 편집하지 않습니다.

3

Plugin-local setup

$setup-agent-guard

Skill이 선택한 plugin-local binary의 check, smoke-test가 모두 성공해야 합니다. PATH에 있는 standalone binary가 다른 version이어도 plugin 검증에는 대체 사용하지 않습니다.

4

현재 task의 실제 tool route 확인

Claude 절의 두 sentinel을 현재 task가 실제로 사용하는 shell tool route로 실행합니다. Codex가 functions.exec 같은 orchestration wrapper만 노출하면 바로 그 경로를 시험합니다.

실패 판정: pre marker가 출력되거나 post raw marker가 모델에 보이면, 현재 Codex release의 해당 route는 보호되지 않습니다. Plugin-local smoke가 통과해도 host setup 완료로 보고하지 말고 Git hook과 CI를 필수 backstop으로 유지합니다.
5

업데이트

codex plugin marketplace upgrade agent-guard
codex plugin list --marketplace agent-guard

Codex CLI 0.144.5에는 별도 plugin update 명령이 없고 marketplace snapshot을 갱신합니다. 갱신 후 새 세션을 시작하고, Settings > Hooks에서 Modified hook을 다시 검토·trust한 뒤 setup과 live probes를 반복합니다.

Marketplace 이름 충돌이 날 때 
codex plugin marketplace list --json
codex plugin list --available --json

먼저 이름, source, root를 확인합니다. 출력에 없는 marketplace를 추측으로 삭제하거나 다른 marketplace를 지우지 않습니다. 실제로 잘못된 agent-guard source가 확인된 경우에만 config를 백업한 뒤 codex plugin marketplace remove agent-guard하고 올바른 source를 다시 추가합니다.

8. Native Git pre-commit hook

Agent/host hook이 닿지 않는 경로를 commit 직전에 차단합니다. 기존 core.hooksPath를 임의로 덮어쓰지 않으며, 충돌하면 설치가 중단됩니다.

1

프로젝트에 설치

cd <your-project>
~/.agent-guard/install.sh git-hooks
git config --get core.hooksPath
test -x githooks/pre-commit

Clone에서 작업한다면 ./install.sh git-hooks를 사용합니다. 예상 설정은 core.hooksPath=githooks입니다.

2

격리된 임시 저장소에서 실제 차단 확인

실제 credential 대신 gitleaks가 인식하는 명백한 synthetic fixture를 사용합니다.

ag_probe="$(mktemp -d)"
git init "$ag_probe"
cd "$ag_probe"
~/.agent-guard/install.sh git-hooks
{
  printf '%s%s\n' '-----BEGIN RSA ' 'PRIVATE KEY-----'
  printf '%s\n' 'AGENT-GUARD-FIXTURE-NEVER-A-REAL-KEY'
  printf '%s%s\n' '-----END RSA ' 'PRIVATE KEY-----'
} > synthetic-private-key.txt
git add synthetic-private-key.txt
git -c user.name='Agent Guard Probe' \
    -c user.email='probe@example.invalid' \
    commit -m 'agent guard negative probe'

성공 신호: commit이 non-zero로 실패하고 secret detection 메시지가 나옵니다. Probe 파일은 임시 저장소 밖으로 복사하거나 push하지 않습니다.

3

CLI 업데이트 후 hook 경로 refresh

cd <your-project>
~/.agent-guard/install.sh git-hooks
grep 'agent-guard.*scan-staged' githooks/pre-commit

재실행은 Agent Guard 실행 경로만 안전하게 갱신하고 기존 legacy hook chain과 로컬 편집을 보존합니다.

9. GitHub Actions

CI에서는 action이 runner의 기존 gitleaks를 사용하거나, 없으면 고정 version과 SHA-256으로 설치합니다. require-checksum 기본값은 true입니다.

1

Runner에 맞는 checksum 조회

agent-guard checksum 8.30.1

GitHub-hosted Ubuntu runner는 보통 linux/x64 값을 사용합니다. 출력된 archive 이름과 workflow의 runner OS/architecture가 일치하는지 확인합니다.

2

Workflow 추가

name: agent-guard
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false
      - uses: JeongJaeSoon/agent-guard@v3
        with:
          paths: "."
          gitleaks-version: "8.30.1"
          gitleaks-checksum: "<linux/x64 archive sha256>"

paths는 whitespace로 나뉘므로 공백이 포함된 개별 경로는 지원하지 않습니다. 전체 저장소를 뜻하는 .가 가장 안전한 기본값입니다.

3

Positive와 negative 경로 모두 검증

  1. Clean branch/PR에서 workflow가 성공하는지 확인합니다.
  2. 격리된 test branch에 Git hook 절의 synthetic fixture를 추가합니다.
  3. Workflow가 gitleaks finding과 함께 실패하는지 확인합니다.
  4. Fixture commit/branch를 제거하고 실제 credential이 전혀 사용되지 않았는지 재확인합니다.

3 또는 dependency 오류를 “탐지 없음”으로 해석하면 안 됩니다. Action step은 non-zero 상태를 그대로 실패로 남겨야 합니다.

4

Version pin 전략

  • @v3: 호환되는 3.x 보안·버그 수정 자동 수용
  • @v3.1.1: 특정 release 고정
  • @<full-commit-sha>: 공급망 변경을 가장 엄격히 통제

조직 정책에 따라 선택하되, 업데이트 후 positive/negative 두 경로를 다시 실행합니다.

10. Sub-agent 경계 확인

Agent Guard는 sub-agent를 생성·스케줄·감독하는 orchestrator가 아닙니다. Parent가 sub-agent에 전달하는 Agent와 legacy Task 입력, 그리고 반환 결과가 기존 Pre/Post 경계로 다시 들어올 때 검사합니다.

입력 경계

Parent가 delegation prompt에 secret-like 값을 넣으면 sub-agent가 시작되기 전에 차단돼야 합니다. 실제 secret을 넣지 말고 setup skill의 pre sentinel 또는 저장소 test fixture를 사용합니다.

출력 경계

Sub-agent 결과에 secret-like 값이나 post sentinel이 있으면 parent 모델에 raw 값이 도달하지 않고 redaction/sanitized replacement가 전달돼야 합니다.

Host별 수동 probe

  1. 새 세션에서 plugin-local check와 smoke-test를 먼저 통과시킵니다.
  2. Parent에게 “sub-agent를 사용해 public API 구조를 요약”하도록 요청하고 정상 delegation이 허용되는지 확인합니다.
  3. Setup skill이 제공하는 harmless pre/post sentinel을 sub-agent 경계에 사용합니다.
  4. 차단/redaction 메시지에 subagent delegation input 또는 sanitized output 신호가 있는지 확인합니다.
  5. Host가 Agent/Task call을 plugin hook에 전달하지 않는 release라면 해당 범위를 미지원으로 기록하고 Git/CI backstop을 유지합니다.
중요: Parent boundary 검증과 sub-agent 내부 tool-call 검증은 서로 다른 증거입니다. 둘 중 하나만 통과했다고 전체 sub-agent 경로가 보호된다고 결론 내리지 않습니다.
