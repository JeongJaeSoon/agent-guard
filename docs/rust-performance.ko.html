Rust 전환, 어디까지 좋아졌나

마스킹 강도를 유지하면서 병목을 검증·개선하고, 측정 근거에 따라 Rust 도입 범위를 결정합니다. 최적화된 셸과 선택형 Rust 코어를 같은 Docker 환경에서 비교했습니다.

판정과 적용 범위

문자열 치환 코어만 Rust로 옮겼습니다. 탐지 규칙, 스캐너, PII, 정책과 호스트 envelope는 기존 구현을 사용합니다. 기본 실행은 셸이며 Rust가 없거나 실패하면 기존 jq로 복귀합니다.

핵심 경로의 목표는 지연 또는 CPU 10% 이상 개선입니다. 일반 경로의 지연 5% 초과 증가 항목: 없음. 차이가 작은 항목은 표본 변동까지 확인해야 합니다.

전체 Rust 재작성이나 모든 플랫폼의 성능 향상을 입증한 결과는 아닙니다. 일반 사용자는 사전 빌드된 바이너리를 실행할 때 Rust 설치가 필요 없지만, 플랫폼별 배포·설치 통합은 아직 후속 과제입니다.

실제 CLI · 시나리오별 비교

기준 셸 = 100%. small-clean은 정상 출력, many-replacement-leaves는 다수 문자열 치환, pre-*는 입력 검사입니다. 낮을수록 사용 시간·자원이 적습니다. 두 구현은 같은 입력을 받고 매 호출의 전체 기대값을 검사합니다. Rust가 호출되지 않는 정상 경로의 차이는 코어 개선 효과로 보지 않습니다. CPU는 user + system 시간입니다.

코어 자체의 효과

15회 교대 측정 중앙값. 프로세스 시작·JSON 입출력 포함, 스캐너와 전체 셸 파이프라인 제외. 이 배수를 전체 CLI의 배수로 읽으면 안 됩니다.

다수 문자열 치환 코어: 327.4 → 2.8 ms. 이 구간에서 줄어든 시간이 전체 CLI의 감소 폭을 대부분 설명합니다.

동시 부하와 프로세스 메모리

실제 실행 환경은 상위 4 CPU·16 GiB 한도를 공유합니다. rootless Docker의 cgroup driver가 none이어서 요청한 컨테이너별 2 CPU·1 GiB 제한은 적용되지 않았습니다. 요청 8개를 worker 1개/4개로 실행, 각각 새 컨테이너에서 3회 교대 반복. 왼쪽은 높을수록 좋고, 오른쪽은 낮을수록 좋습니다. 메모리는 10 ms마다 컨테이너 내부 프로세스 RSS를 합산한 최대 표본입니다. 드라이버·init을 포함하고 공유 페이지는 중복 계산될 수 있으며 순간 peak는 놓칠 수 있습니다. 페이지 캐시·Docker daemon·빌드는 제외합니다. 샘플러 비용은 양쪽에 포함됩니다.
